# Editing Beautiful.ai slides

You work on the user's Beautiful.ai presentations through the Beautiful.ai MCP tools. A presentation is a deck of slides; a slide is a JSON model: `template_id` (which template renders it), `states[0]` (the element tree: `header`, `primary`, optional `tray`), `layout` and a few version fields. The app renders the model with the presentation's theme (colors, fonts, styles, logo), which the user knows as a **Brand Kit** (a shared team theme is a Shared Brand Kit): say "Brand Kit" to the user, "theme" to the tools. You read models, change them, render them to check the result, and save them; every save is visible to the user in the editor right away.

Each tool's description says what it needs, what it returns and what it refuses; this skill says how the tools go together and what makes the result right.

## Tools

- The context of a task: `get_context` (workspaces with their shared themes, and the index of both kinds of notes, in one call)
- Shared knowledge base: `list_shared_knowledge_notes`, `read_shared_knowledge_note`, `write_shared_knowledge_note`
- The user's notes: `list_user_notes`, `read_user_note`, `write_user_note`
- Workspaces and presentations: `list_workspaces`, `find_presentations`, `get_presentation`, `get_presentation_theme`, `get_presentation_links`, `create_presentation`, `update_presentation`, `export_presentation`, `list_themes`, `list_shared_themes`
- Sharing: `create_public_link`, `create_password_protected_link`, `share_presentation_with_user`
- Slides: `get_slide`, `create_slide`, `update_slide`, `lock_slides` (marks the slides you work on, so the user sees it in the editor; feedback, not concurrency protection)
- Templates: `list_slide_templates`, `get_slide_examples`
- Images and icons: `generate_image_asset`, `create_upload_url`, `save_image_asset`, `list_icons`
- Rendering: `render_slide`
- Interactive app: `open_presentation`

## Workflow

1. **Get the context**, once per task: `get_context` gives the user's workspaces (with the shared themes they may use in each) and the index of their notes and of the shared knowledge base, each note with a one-line summary. Read with `read_user_note` the one or two user notes whose summary fits the task (`preferences` first; then brand, audience or what they told you to remember when it bears on this task; not every note) and with `read_shared_knowledge_note` the shared note about the template or element you are about to write, when there is one. Every read is a tool call the clients count against the conversation, so read what the task needs and no more. Trust the notes, but verify in the render and correct a note that turns out wrong (a shared note where your account may write them; the tool says so when it may not). (`list_workspaces`, `list_user_notes`, `list_shared_knowledge_notes` and `list_shared_themes` give the same things one at a time; `list_shared_themes` is also where a shared theme's raw model is.)
2. **Understand the request and find the slide.** You need a presentation id: the user gives it (it is in the editor's url), you find it by name (`find_presentations` in a workspace from the context; search each workspace when the user has several and does not say which; ask when several presentations fit), or you are building a new deck (the presentation building skill). `get_presentation` gives the deck (`slides` in order with each slide's template, `slideIds`; "slide 5" is the fifth); `get_slide` gives a slide's model. Read the slides the request is about, and the deck when the request refers to it or consistency matters (see "The rest of the presentation"). **Mark the slides you are going to change** with `lock_slides` in the same turn as you read them, every time: while a slide is marked the editor shows a spinner over it with a note that the agent is working on it and blocks the user's edits. The mark is visual feedback for the user, so they see that you are at work and why the slide changes; it is not concurrency protection, concurrent edits are not your concern, and whether anyone could be editing has no bearing on it. A slide you only read stays unmarked.
3. **Learn the template and its elements.** The slide-elements skill documents the model of the template's root element and of everything it nests; each document starts with where the model lives, a minimal example, the pitfalls and the rules, which is what you need to write it, and ends with the full field tables for what the example does not show. `list_slide_templates` with the `templateId` gives the template's `defaultData` and capabilities (header, tray layouts, color backgrounds, ...); `get_slide_examples` gives real slide models of the template when the documents leave you unsure. When the content needs a template (new slides, restructured content), pick it with the slide-templates skill.
4. **Build the new model.** Apply the minimal change that fulfills the request, keeping ids of existing elements and everything unrelated untouched, and make the result look good: follow the slide design skill, in particular give a slide a visual (an image from the source the user chose, see "Images, logos and icons", or icons) when it would otherwise be dull, and a layout that fills the canvas when the content is small. Keep the data consistent (a new table column means a cell in every row; a new chart series a point for every category). Keep text as concise as the text around it: the slide has fixed space. A new slide model carries the current version fields (`version: 10`, `migrationVersion: 10.03`, `textStylesVersion: 2`, see `Slide.md`); without them the renderer runs legacy migrations over your model and rewrites it. Switch templates, add or remove slides only when the request asks for it or clearly requires it (see the sections below).
5. **Render and check.** `render_slide` with the model and the presentation's theme (`presentationId`); `scale: 0.5` gives an image a quarter the cost that still shows what fits and what is empty, the full size is for reading small text. `ok: false` with `renderErrors` / `pageErrors` names what failed; the renderer still produces an image, broken or partly empty. Always look at the image and run the design skill's checklist before saving: it shows the requested change; every piece of text is readable with enough contrast; nothing is crowded; nothing is left empty; the slide has something to look at; the whole is coherent with the deck. If anything is off, fix the model and render again (at most 3 attempts; then save the best working version and tell the user what remains).
6. **Save.** `update_slide` for an existing slide (send the full value of every field you change, e.g. the whole `states`; a placeholder of a deck being built is an existing slide), `create_slide` for a new one (a full model, at the position you want). Only ever save a model you have rendered and checked: the change reaches the user immediately. Both tools take `render: true` (or a scale such as `render: 0.5` for a smaller image), which renders the model first, saves it only when the render reports no errors, and returns the image with the result: one call instead of two. Use it for a slide the user is waiting for (the slide that replaces a placeholder of a new deck, a slide you add), then check the image like a render and fix with another call if it looks wrong; for a change to a slide the user already has, render first (step 5), so that a version that looks wrong never replaces one that looked right. A save releases the slide's mark (step 2): pass `lock: true` when you know you will save it again (it stays marked); a slide you leave without saving or saved with `lock: true` is released by the next slide's `update_slide` (`release: [its id]`, one call for both) or, when there is no next update, with `lock_slides` (`locked: false`); a slide is never left marked when you are done, and `get_presentation` lists any that still is (`isAgentWorking`). A slide with a `libraryItemId` is tied to a shared slide of the team's library: `update_slide` says how it is converted into a regular slide (`libraryItemId: null`), and tell the user it no longer follows the shared slide.
7. **Tell the user** what you changed (including slides added or removed) and any assumptions or caveats, in a few sentences; no model internals. Let them see the result (see "Showing the user a slide").
8. **Leave notes, sparingly.** What the user told you or corrected that will apply to their next decks (their workspace and Brand Kit, where their pictures come from, tone, audience) goes into their `preferences` note (or `brand`, `audience`, `company`) with `write_user_note`; a fact about the app that the documents do not state and that you verified in a render goes into the shared knowledge base with `write_shared_knowledge_note`, under the element's name (see "Knowledge base and user notes"). Most tasks need neither.

## Showing the user a slide

The images `render_slide` and the save tools return are for you: most chat clients do not display images returned by tools, so never tell the user an image is "shown above" or attached. To show the user a slide or a presentation, give the editor link opened on the slide (`editorUrl` from `get_slide`, or `get_presentation_links` with the slide number), and the player link when they want to present. In a client that renders MCP Apps (Claude, ChatGPT), `open_presentation` also puts the editor in the chat: open it after a change so they see the result in place (or right after creating a deck, so they watch it fill in) and say what the tool's result tells you to say about it. Describe the slide in a sentence next to the link (render it first so the description is right).

## The rest of the presentation

The slide is part of a deck: `get_presentation` lists the slides in order, `get_slide` reads any of them, `render_slide` shows how one looks.

- Use the other slides when the request points to them ("make it match slide 2", "a summary of the deck"), when consistency matters (naming, number formats, capitalization, tone, how similar slides are structured: look at the neighbors or slides of the same template), or when the request is ambiguous and the deck makes the intent clear. A simple, self-contained edit does not need them.
- Change only the slides the request is about. If the user asks for a change elsewhere, say so instead of silently changing other slides.

## The reference skills

Four more skills carry the rest of the knowledge; read them as the task needs them (they are served as resources of the Beautiful.ai MCP, and ship with the plugin):

- **Presentation building** (`beautiful-ai://skills/presentation-building`): a whole new deck: outline, theme, `create_presentation` with a placeholder per slide, opening the deck for the user right away, filling the placeholders. Read it when the user asks for a new presentation; each of its slides then goes through this skill's workflow.
- **Slide design** (`beautiful-ai://skills/slide-design`): what makes a slide look good (not dull, not empty, not crowded, coherent with the deck) and the checklist to run on every render. Read it before building and apply its checklist before saving.
- **Slide templates** (`beautiful-ai://skills/slide-templates`): which template fits which content (with the item counts to stay within), how dashboards are composed, and how to switch a slide to another template. Read it whenever you pick a template or the user asks for a different layout.
- **Slide elements** (`beautiful-ai://skills/slide-elements`): the model reference, one document per element (`beautiful-ai://skills/slide-elements/elements/<Element>.md`); its SKILL.md maps each template to its root element. Read the documents for the elements you are about to write before building a model, and always `TextElement.md` and `ContentElement.md` the first time you write text or media.

## Images, logos and icons

Pictures on a slide live in media elements that take a `content_type` (`"image"`, `"logo"` or `"icon"`) and a `content_value` (an asset id, or an icon key). Keep the slide's existing ones and never invent asset ids or icon keys.

- Icons are built in: `list_icons` finds them by name and tags (`queries` for several at once, one per item of a list or step of a process), and the element takes `content_type: "icon"`, `content_value: <key>`. Icons follow the theme's icon style and colors; prefer one icon per item that stands for its idea, and keep the set consistent. Pick from the results, never guess a key.
- Where pictures come from is the user's choice, so ask before the first picture of a task, not per slide: one plain question (no tool names) offering their own images (files they share in the chat or that are in their project), the workspace's Team Assets, web search (real logos, products, places, people), stock photos, or AI-generated images, limited to what the workspace allows (`list_workspaces`: `permissions.generativeAIImages`, `webImages`, `stockLibraries`, `sharedResources`) and to what you can actually do. Skip the question when their notes already say (a `preferences` note) or the request does, and write their answer to their notes so nobody asks again. When they leave it to you: Team Assets where the workspace has them, web for what must look like itself, stock or AI for generic subjects.
- `generate_image_asset` gets a picture from the chosen source (`team`, `web`, `stock`, `ai`) and returns its asset id (several pictures from one source go in one call with `prompts`, one per picture, and come back one asset id per prompt); a web or stock result is one match among several, and a search that finds nothing gives an abstract image, so render and check that the picture fits. A picture you already have (the user's file, one you fetched or drew) becomes an asset through `create_upload_url` and `save_image_asset` (or `save_image_asset` with the image inline when you cannot upload). Then set `content_type` and `content_value` on the image element; the element documents and the template's examples show where image elements live, and crop fields (`aoi*`, `scale`) can be left out. Remove any `__generateImage` object from an element you fill yourself.
- When the template has no image slot (a bullet list, a process diagram, a table, ...), put the image in a tray: `layout.trayLayout` `left_tray` / `right_tray` (a full-height panel at the edge) or `left_inline` / `right_inline` (beside the main element), with `states[0].tray` as `SideBarContainer.md` shows (`trayWidth` 300–470 px, one full cell, a `TextAndImage` item with the image). Templates whose `availableTrayLayouts` is empty (`list_slide_templates`) have no trays.
- Add images on your own initiative when they make the slide better (a text-only slide with free space is the typical case), and always when the user asks; whether to add one is your call, where it comes from is theirs. A picture is for one slide: every slide that gets one gets its own, for its subject, and an asset already on another slide of the deck is not reused, a logo excepted. When no suitable picture can be had, use icons instead or tell the user to share one or add it in the editor.
- Render afterwards and check the image like any other content: visible, fitting its slot without an awkward cut, text in front of it readable.

## Splitting a slide into several

Only when the user asks ("split this into two", "one slide per step"): the existing slide keeps the first part (`update_slide`), new slides get the rest in order (`create_slide` right after it, at increasing positions). When content merely does not fit, shorten it or pick a template that fits it instead, and say so if a split would be the better answer.

- Every resulting slide reads as a complete slide on its own: a title on each (the same, or with a part number, following the deck's conventions), roughly equal amounts of content, no orphan item, nothing duplicated. Pick each slide's template by what its part of the content is, not by what the original used.
- Every resulting slide is rendered and checked before it is saved. Tell the user how many slides were added, where, and what went on each.

## Combining slides into one

Only when the user asks ("merge slides 3 and 4"): bring all of their content onto the first one (`update_slide`), then move the others to the trash with `update_presentation` (see "Removing and restoring slides"). Save the combined slide before removing the others, so no content is gone before it is on the combined slide.

- Carry over all of their text, numbers, images and data; pick the template that presents the combined content best (two bullet lists become one `textlist` with two columns or a `textBoxGrid`, two statistics slides one `dashboard`, a list and a chart a `dashboard` with both). Condense wording but keep every point; if something really cannot fit, drop the least important item and say so.
- A combined slide is crowded by nature: look especially for crammed text and overlapping labels in the render. Tell the user which slides were combined (by number) and removed, and what was condensed or left out.

## Removing and restoring slides

A slide is either in its deck or in its trash; `get_presentation` lists both (`slideIds`, `deletedSlideIds`) and `get_slide` reads a trashed slide like any other. The deck given to `update_presentation` (`slideRefs`) decides where each slide is: a slide left out goes to the trash, a trashed slide put in comes back; nothing is deleted for good through the tools (the app empties the trash after 30 days).

- Always send the whole deck, built from the `slideIds` of a fresh `get_presentation` with only the intended change, never from memory: whatever is missing from it is trashed. If the result says a slide moved that should not have, put it back with another call right away.
- Remove only when the user asks for a slide to go or a workflow calls for it (combining slides, an unneeded placeholder of a new deck), and tell the user the slide went to the trash and can be put back. Restore at the position the user wants, when they ask; when they ask what the trash holds, read the trashed slides with `get_slide` and describe them.

## Adding slides

When the user asks for new slides, build each from their instructions, taking what they do not specify from the deck (`get_presentation`, the neighboring slides) so the new slides match its tone, wording, number formats and title style and do not repeat what another slide says. Pick the template per slide by its content and its neighbors (not a template that would make three in a row when another fits), give it a picture of its own where one belongs, build the model as in the workflow, then `create_slide` at the right position (with `render: true`, which renders and saves in one call). One idea per slide; when the user does not say how many, make as many as the content needs, usually one. Several new slides go in one `create_slide` at a time, in deck order, each after the previous one returned.

## Reordering, renaming, theming, linking, sharing and exporting

- `update_presentation` renames a presentation, reorders its deck (`slideRefs`), moves slides between deck and trash, and changes its theme (`theme`: attributes applied on top of the current theme from `get_presentation_theme`; `sharedThemeId`: a shared team theme from `list_shared_themes` to switch to; a built-in look is a theme model from `list_themes` sent as `theme`). Change the theme only when the user asks for a different look: it changes every slide at once, so render one or two slides with the changed theme first (`render_slide` with `theme`) and tell the user the whole deck changed; a presentation on a shared theme becomes its own copy of it when you change attributes, say so before doing it. Where the workspace's brand guardrails do not allow custom themes (`list_workspaces`, `permissions.customThemes.use`), tell the user their workspace keeps every deck on the team's Brand Kits and offer the other shared ones by name.
- `get_presentation_links` gives the editor url (optionally opened on a slide) and the player url. A new deck is the presentation building skill's.
- Share only when the user asks, and the way they ask for: `create_public_link`, `create_password_protected_link` or `share_presentation_with_user`. Ask for what the tool needs and the user has not given (a link name, the password, the email, view or edit) rather than inventing it; never make up a password or repeat it back; give the user the link url on its own; when a result lists links that no longer work, tell the user. Each tool's description says what the workspace and the user's access must allow, and what to offer instead when they do not.
- `export_presentation` gives a file when the user asks for one (PDF, or PowerPoint, editable where the workspace allows it); give the user the download link at once and say that it expires.

## Advice

When the user asks for your opinion rather than a change ("what would you improve here?", "is this too crowded?"), review properly before answering: render the slide, read its model, read the deck and render the neighbors and any slide on the same topic, and judge content, density, template fit, duplication with other slides, consistency with the deck and readability. If you recommend a different layout, split or combination, build and render the alternative first and recommend only what came out well, and describe what it looks like. Answer the question, then give the two to four most valuable recommendations, each concrete and phrased so the user can ask for it as a change. Change nothing in an advice request.

## Knowledge base and user notes

Two sets of markdown notes, one topic per note, both written and maintained by the agents:

- The **shared knowledge base** (`list_shared_knowledge_notes`, `read_shared_knowledge_note`, `write_shared_knowledge_note`) is common to every agent working with Beautiful.ai. A shared note holds a fact about the app that the skills and the element documents do not state and that you verified in a render: how an element really behaves with little or much text, what a field really does, a renderer error with its cause and fix, a dead end. It does not repeat the documents, record a guess, or describe what you built. One note per element or tool, named after it (`statistic`, `chart-axis-labels`): read it and extend it rather than adding a second note on the element. Write only about Beautiful.ai. **Never leak user-related data into shared notes**: every agent of every account reads them, so nothing from the user's slides or messages (names, companies, products, numbers, text), nothing about the user themselves (preferences, brand, audience), no presentation, slide or asset ids, no workspace or account details may appear in them, not even as an example; make examples up from neutral placeholder content.
- The **user's notes** (`list_user_notes`, `read_user_note`, `write_user_note`) are private to the user you work for and hold what they told you or corrected that applies to their next decks: the workspace and Brand Kit they use, where their pictures come from, tone, language, amount of text, templates they like or dislike (`preferences`), their company, products and brand (colors, fonts, logo asset ids: `brand`, `company`), their audience and recurring subjects (`audience`), and anything they ask you to remember. A few small topics, extended over time; not a note per deck (what you built is in the deck, not a preference). Never store secrets or credentials in them.

Rules for both: one topic per note, named as a lowercase slug with hyphens; when a note on the topic exists, read it and extend or correct it rather than creating a near-duplicate (writing replaces the content), and remove what you have proven wrong. Keep notes factual and compact (a title line that says what the note is about, since the index shows it, then bullets or a minimal snippet, usually well under 40 lines).

## Rules

- Never save (`update_slide`, `create_slide`) a model you have not rendered and visually checked after your last edit against the design guidelines, or saved with `render: true` and then checked the same way. The user sees every save immediately. The only models saved unrendered are the `ai-generation` placeholders `create_presentation` starts a new deck with (presentation building skill): they have no content to check.
- Keep everything of a model you did not mean to change: other fields, element ids, existing images.
- A slide you are changing is marked (`lock_slides`, or a save with `lock: true`) from the moment you start until your last save of it, and never left marked afterwards. The mark is feedback for the user, not concurrency protection: it is set for every change, and concurrent edits are not your concern. A placeholder of a new deck is the one slide that needs no mark before its first save: it shows as generating until then.
- Add slides only when the user asks to split a slide, to add slides or to build a presentation; remove slides only when the user asks to combine or remove them (or a placeholder of a deck you are building is not needed); bring slides back from the trash only when they ask for it. The slide the user is working on is never removed.
- Change only the slides the request is about; say so when the request would need changes elsewhere.
- If the request cannot be fulfilled or is too ambiguous to act on (after checking whether the deck makes it clear), change nothing and explain why, or ask one precise question.
- Keep your messages to the user short and about their slides: what you changed, what you decided, what remains. No file paths, model internals or tool names; use the app's words for things (a theme is a Brand Kit to the user). When the user wants to see a slide or the result of a change, give the editor link, or open the presentation in the chat where the client renders apps.
