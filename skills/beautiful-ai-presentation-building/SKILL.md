# Building a Beautiful.ai presentation

When the user asks for a whole presentation ("make me a deck about X", "a 10-slide pitch for ...", "turn these notes into a presentation"), you create the presentation with a placeholder for every slide as soon as you know how many slides there are and what each says, then plan the slides' templates and visuals and build them one by one into their placeholders. The slide work itself (model, render, check, save) is the slide editing skill's workflow; this skill is about the deck: what goes in it, in which order, and how to keep the user in the loop while it takes shape.

## The other skills

- **Slide editing** (`beautiful-ai://skills/slide-editing`): the workflow for every slide you build (notes, element reference, build, render and check, save, notes), the tools, and the rules. Each slide of the deck goes through it.
- **Slide templates** (`beautiful-ai://skills/slide-templates`): which template fits which content; pick the template of each slide with it.
- **Slide design** (`beautiful-ai://skills/slide-design`): what makes a slide look good and the checklist to run on every render; the deck is only as good as its slides.
- **Slide elements** (`beautiful-ai://skills/slide-elements`): the model reference for the elements you write.

## Steps

1. **Outline the deck: its slides, nothing more.** Get the context first (`get_context`: the workspaces with their shared themes, and the index of the user's notes and of the shared knowledge base) and read the one or two user notes whose summary fits the deck (`read_user_note`: `preferences` when there is one, then the one about the brand or the audience when it matters here; not every note, and no shared note at this point): their preferences, brand and audience decide much of what follows (tone, language, theme, how much text, what to avoid), so you ask less and get it right the first time. Then the outline: how many slides, and one line for each saying what it will say, in a sensible order: a title slide, the story (context, problem, solution, evidence, plan, ...), a closing or next-steps slide. When the user does not say how many slides, make as many as the content needs: typically 6–12, one idea per slide, no filler. That outline is all the deck needs to be created: do not pick templates, layouts or pictures yet (step 5 does, once the user can already see the deck). Ask only when the request leaves out something you cannot decide well yourself (the audience, the number of slides, must-have content) and for the two things that are the user's call: where the deck's pictures come from (their own images, the workspace's Team Assets, the web, stock photos or AI; see the editing skill's images section), and, when the workspace has shared themes (step 2), which Brand Kit (the user's word for a theme) to use, naming the team's default one as the default and, where the workspace's brand guardrails allow only shared themes, saying so; unless their notes or the request already say. Ask everything in one message, before creating the deck, decide the rest yourself and tell the user what you assumed. When nothing needs asking, go straight on to creating the deck.
2. **Pick the theme.** To the user a theme is a **Brand Kit** (the app's name for it; "theme" is the tools' internal name for the same thing), so that is the word to use with them. The context (`get_context`) lists the shared themes of each workspace: these are the team's own Shared Brand Kits (null where the user may not use shared themes). When there are shared themes, the user decides: ask them, in the outline message of step 1, naming the shared themes, the default one first and as the default ("your team's default Brand Kit, X, unless you prefer another"), unless their notes or the request already say. Whether a built-in look is an alternative depends on the workspace's brand guardrails (the workspace's `permissions.customThemes.use` in the context): where custom themes are not allowed, built-in themes are out and the deck has to use one of the shared themes, so say so in the same question ("your workspace's brand guardrails keep decks on the team's Brand Kits") and do not offer a built-in look; otherwise offer it. A shared theme is the usual choice of a team that has them; a deck on it follows the theme when the team updates it. For a built-in look (the user's choice, or a workspace without shared themes), `list_themes` lists the built-in themes (palette, fonts, style); choose the one the user's notes name, else what the user asked for ("something dark and modern") or one that fits the subject and audience; Classic is the safe default. Either kind has a raw theme model (`list_shared_themes` for a shared theme, `list_themes` with the id for a built-in one), which lets you render a slide with it (`render_slide` with `theme`) when you want to see it before deciding.
3. **Create the presentation as a deck of placeholders, as soon as the count and the theme are known** (right after the user's answer, or at once when nothing needed asking): the user should see their deck taking shape before you have thought about any slide's details. `create_presentation` takes a name that says what the deck is about, the workspace id from the context (ask which one when the user has several and the request does not say), the theme (`sharedThemeId` for a shared theme, `themeId` for a built-in one) and `slides`: one placeholder model per slide of step 1, in deck order, its `slidePrompt` the slide's one line. A placeholder is `{ "template_id": "ai-generation", "states": [{}], "metadata": { "isGenerating": true, "slidePrompt": "<one line: what this slide will say>" } }` plus the version fields of any new slide model (`Slide.md` in the elements reference); it has no content to render or check. In the editor every placeholder shows "Generating slide..." until you replace it. The tool returns the presentation id, `slideIds` in deck order (the n-th id is the n-th slide of your outline) and the editor url: keep the ids, they are the slides you are about to fill.
4. **Open the deck for the user.** Right after creating it, call `open_presentation`: in a client that renders MCP Apps the app appears in the chat with a button that opens the editor fullscreen, showing the whole deck as placeholders that turn into finished slides as you save them. In the same message give the editor link (`editorUrl`, from `create_presentation` or from `open_presentation`'s result) and recommend it: the editor open in its own browser tab next to the chat is the better way to watch the deck being built (it updates live as you save, and the conversation stays visible, which it does not while the in-chat editor is fullscreen); the button in the chat is the alternative. The link is also all a client that does not render apps shows, and the fallback if `open_presentation` fails. Say that the deck is being built and will be ready in a few minutes; this is the last thing you say to the user until the deck is done (step 6).
5. **Plan the slides, then fill the placeholders.** With the deck created and open, decide the rest: the deck's tone and how much text a slide carries, and for each slide its template (the slide templates skill) and what it needs beyond text (a chart, a table, a picture, icons). Pick the templates for the deck as a whole, not one slide at a time: a deck whose slides all look alike (the same template and layout slide after slide) is the most common way a generated deck disappoints, and the user expects variety without asking for it. Two neighboring slides on the same template are fine when their content calls for it; what to avoid is many slides that look identical: a run of three or more on the same template, or a template on more than about a third of the deck. When a template would repeat that much, give one of the slides the alternative the templates skill lists for that content or restructure it; when it repeats at all, plan a different layout for the two so they do not come out identical (see "Varied across the deck" in the slide design skill). Plan the pictures the same way: which slides get one, what each shows, and each its own. This planning is thinking, not tool calls, and the user already has the deck in front of them while it happens; the one call before the slides is for the deck's pictures: get them all at once, one `generate_image_asset` call with `prompts` (one prompt per slide that gets a picture, in deck order, from the source the user chose in step 1; its result lists an asset id per prompt, and a prompt that got none is retried alone, with other words or another source, when you reach its slide), so that each slide's picture is at hand when you build it; the user's own files are uploaded and saved one by one. Then fill the placeholders with `update_slide`, in deck order, each slide built, rendered and checked as in the slide editing workflow, **all of them, in one go**: never stop after a few slides to ask whether to continue, to report progress, or to check that the direction is right. The user asked for the whole deck, every question that was theirs to answer was asked in step 1, and a deck left half placeholders is not a result; the next message you send is the one of step 6, when every placeholder is filled. The only reason to stop earlier is a tool refusing to go on (a rate limit, a lost connection), and then say exactly which slides remain. The first is the title slide: a `title` template slide, kept simple (the presentation title and, when the request gives them, a subtitle and the presenter or date; no pictures or extras unless the user asked; `PresentationTitle.md` in the elements reference, a `title` example). For every slide, `update_slide` on its id from step 3 with the full model: `template_id`, `states`, `layout`, the version fields, and `metadata` with `isGenerating: false` (it replaces the placeholder's metadata; a slide left with `isGenerating: true` keeps showing as generating in the slide navigator and gets no thumbnail). There is no need to read a placeholder first (`get_slide`): it has nothing to keep, and no need to mark it first (`lock_slides`): it shows as generating until this save. Make that `update_slide` call with `render: true` and `lock: true`: the slide's model is rendered with the deck's theme and saved only when the render reports no errors, and the image comes back with the result, so one call does what `render_slide` and a save would; the slide stays marked as being worked on (a spinner over it in the editor, so the user sees you are still at work on it; feedback, not concurrency protection) while you check the image against the design checklist and, when something is off, fix the model and call `update_slide` again (at most 3 attempts, as in the editing workflow). When the slide is done and you move on, the next slide's `update_slide` releases it: pass `release: [<the finished slide's id>]` on that call, and again on the retry when the first attempt did not save (a save releases only once it is done; its result says what it released), no separate `lock_slides` call; only the last slide, once its image checks out, is released with `lock_slides` (`locked: false`), the one `lock_slides` call of a build. Never `create_slide` for a slide of the outline: its placeholder already exists. Keep each slide consistent with the ones before it in style (the same title style, wording, number formats, icon style and level of detail, no two slides saying the same thing) and different from them in structure: build it on the template and layout your plan gave it, and when it ends up on the same template as the slide before it, make it look different before saving (the other tray side or none, the other header position; the alternative template when it would be the third in a row). Give slides visuals where the design guidelines call for them, from the pictures you got up front (or the user's files), every slide its own: an asset that is already on a slide of the deck does not go on another; a logo is the one exception.
6. **Finish.** No placeholder and no marked slide may be left: every save of step 5 told you what it saved and released, so when every slide went through cleanly and the last one is released, you know it without another call; only when something went off (a save that failed and was not retried, a release the result did not confirm, a slide you skipped) does `get_presentation` list the deck with `isGenerating` and `isAgentWorking` per slide, one call to check and settle it (release what is still marked with `lock_slides`). A slide that did not come out well is saved in its best working version, and a placeholder you end up not needing is moved to the trash (`update_presentation` with a `slideRefs` without it, see "Removing and restoring slides" in the editing skill). Tell the user what the deck contains (one line per slide is plenty) and what you assumed, and give the editor link again, the one `create_presentation` returned, without calling `get_presentation_links` (that is for when the user asks for the player link or a link opened on a slide); the open editor already shows the finished deck, so do not open it a second time. Leave notes as the editing skill asks, sparingly: what the user chose or corrected that applies to their next decks (the workspace, the Brand Kit, where their pictures come from, the audience they present to) in their `preferences` note; a fact about the app the documents do not state, verified in a render, in the shared knowledge base. Not a note about this deck.

## Rules

- The deck is created as soon as its slide count and theme are known, before any slide's template, layout or picture is decided: creating it needs nothing more, and the user gets to see it (the editor link, recommended for its own tab, and the editor in the chat where the client renders apps) right away, as placeholders that fill in one by one, not at the end.
- The presentation is created with a placeholder (`template_id` `ai-generation`, `metadata.isGenerating: true`) for every slide of the outline, and each one is replaced in place with `update_slide` on its id, with `isGenerating` cleared; no placeholder is left behind and none is duplicated with `create_slide`. The first slide is a simple `title` slide, the only title slide of the deck.
- Every slide of the outline is rendered and checked: written over its placeholder with `render: true` and its image checked, or rendered first and then saved. A slide stays marked as being worked on (`lock: true`) until it is done, and is released then, by the next slide's `update_slide` (`release`); none is left marked.
- A deck is built in as few calls as it takes, because the clients cap the tool calls of a conversation and a deck cut off halfway is the worst result: the pictures in one `generate_image_asset` call (`prompts`), each slide in one `update_slide` (`render: true`, `lock: true`, `release` for the slide before), one or two notes read, no call to list the links or check the deck that its results have already answered. The placeholders themselves carry no content and are created unrendered by `create_presentation`. A slide that does not come out well after the attempts the editing skill allows is saved in its best working version and mentioned to the user, not silently dropped.
- The deck is varied without the user asking for it: no run of three or more slides on the same template, no template on more than about a third of the deck, no two neighboring slides with the same template and the same layout, and every picture on one slide only. This is planned for the deck as a whole once it is created (step 5) and checked on every slide before it is saved.
- Build the slides the user asked for and nothing else; when the content is too thin for the number of slides asked, say so and make fewer rather than padding. Settle the count before the placeholders are created; a placeholder that turns out unnecessary is removed from the deck, not left as it is.
- Once the deck is created, it is finished without a pause: no message to the user between step 4 and step 6, however many slides there are, and never a question whether to continue. Everything the user had to decide was asked before the deck was created.
